# Architecture Refactor

## Goal

Restructure the VS Code extension into a clear class-based architecture with predictable module ownership, generated domain types, minimal comments, and a normalized asset layout.

The current code works, but the architecture has started to drift: `FixMyCommentsController` owns too many responsibilities, `extension.ts` manually wires commands and watchers, several pure data types live beside behavior, comments explain obvious code in many places, and `resources/` should become an explicit `assets/` hierarchy.

## Current Issues

### Large mixed-responsibility classes/files

- `src/comments/comment-controller.ts` is a 946-line controller that handles native VS Code thread creation, persistence, message creation, reactions, task toggles, suggestion draft mode, inline helpers, markdown rendering, target parsing, and navigation.
- `src/extension.ts` directly creates providers, trackers, decorators, command registrations, and the storage watcher. Activation is bootstrap logic plus application wiring in one function.
- Helper functions at the bottom of `src/comments/comment-controller.ts` are unrelated concerns grouped by file accident: user factory, labels, anchors, markdown rendering, reaction links, target parsing, and helper messages.

### Comments are too noisy

- Several files contain comments that restate the function name or obvious control flow.
- Keep comments only for contracts and non-obvious behavior, such as the shared `~/.fixmycomments` storage path contract with the MCP server.
- Generated files in `src/generated/` include many generated JSDoc blocks. Do not hand-edit generated output; adjust schema descriptions or generator settings only if we want shorter generated docs.

### Types are split between generated and local files

- Type generation already exists via `type-crafter` (`npm run gen:types`) with YAML schemas under `types/` and output in `src/generated/`.
- Domain/storage data types should stay in YAML and be generated.
- Current manual types to review:
  - `src/comments/comment-controller.ts`: `DraftMode`
  - `src/anchoring/anchor-recovery.ts`: `AnchorState`, `RecoveryResult`
  - `src/anchoring/anchor-tracker.ts`: `LineContentChange`
- Keep purely private implementation helper types local only when they describe class internals. Move cross-module/domain data types into `types/*.yaml` and regenerate.

### Asset layout is generic

- Current assets live in `resources/`:
  - `resources/icon.png`
  - `resources/fix-my-comments.svg`
  - `resources/gutter-comment.svg`
- Target layout should be explicit:

```text
assets/
├── icons/
│   ├── icon.png
│   └── fix-my-comments.svg
└── images/
    └── gutter-comment.svg
```

Update `package.json` contributions and runtime code paths after moving files.

## Scope

In scope:

- Introduce a class-based application structure around activation and feature modules.
- Split comment-thread behavior into focused classes/services.
- Move domain data types to `types/*.yaml` where they can be generated by `type-crafter`.
- Keep module-private behavioral types close to their owning class.
- Remove redundant comments from source files.
- Move `resources/` into `assets/icons/` and `assets/images/`.
- Preserve current user-facing behavior.
- Keep native `vscode.comments` thread UI as the chosen UI direction.

Out of scope:

- Replacing native comments with a webview.
- Changing the storage contract with the MCP server.
- Changing thread/message JSON shape unless a type-generation migration requires it.
- Adding new product features.
- Hand-editing files in `src/generated/` except as temporary debugging.

## Target Architecture

Use module folders with one responsibility each. Every module exposes a small `main.ts` entrypoint. Internal files stay private to the module unless exported from `main.ts`.

```text
src/
├── extension.ts                  # minimal activate/deactivate only
├── lib/
│   └── modules/
│       ├── app/
│       │   ├── main.ts               # public app module exports
│       │   ├── extension-app.ts      # startup, object graph, disposal
│       │   ├── command-registry.ts   # command IDs and registration
│       │   ├── storage-watcher.ts    # external file change refresh
│       │   └── utils.ts              # app-only helpers, if needed
│       ├── comments/
│       │   ├── main.ts               # public comments module exports
│       │   ├── controller.ts         # VS Code CommentController adapter only
│       │   ├── thread-service.ts     # thread lifecycle orchestration
│       │   ├── message-service.ts    # messages, tasks, suggestions, reactions
│       │   ├── draft-mode-service.ts # draft state and helper comments
│       │   ├── renderer.ts           # ReviewMessage -> Markdown/native comment body
│       │   ├── target-resolver.ts    # command target parsing
│       │   └── utils.ts              # comments-only helpers, if needed
│       ├── anchoring/
│       │   ├── main.ts
│       │   ├── engine.ts
│       │   ├── recovery.ts
│       │   ├── tracker.ts
│       │   └── utils.ts
│       ├── storage/
│       │   ├── main.ts
│       │   ├── thread-store.ts
│       │   ├── workspace-identity.ts
│       │   ├── git-info.ts
│       │   └── utils.ts
│       ├── decorations/
│       │   ├── main.ts
│       │   ├── gutter-decorator.ts
│       │   └── utils.ts
│       └── tasks/
│           ├── main.ts
│           ├── tasks-view.ts
│           └── utils.ts
└── generated/                    # generated by type-crafter
```

Module rules:

- `main.ts` is the only public import path for a module.
- `utils.ts` is module-private and must not become a dumping ground.
- Cross-module imports should use `src/lib/modules/<module>/main.ts`, not internal files.
- Do not add a shared helpers folder; if multiple modules need something, move it into the module that owns the concept and export it from that module's `main.ts`.
- Each module owns one concern; split a module if it starts owning unrelated behavior.

## Success Criteria

- `src/extension.ts` only creates an `ExtensionApp`, calls `start()`, and registers it for disposal.
- No single source file remains a mixed controller for rendering, persistence, commands, and domain mutation.
- `FixMyCommentsController` becomes a small adapter around VS Code native comments.
- Command registration is centralized and easy to scan.
- Shared domain/storage types come from `src/generated/` via `type-crafter`.
- New or shared pure-data types are added to `types/*.yaml`, then regenerated with `npm run gen:types`.
- Redundant comments are removed; remaining comments explain contracts or non-obvious behavior.
- `resources/` is replaced by `assets/icons/` and `assets/images/`.
- `package.json` icon/contribution paths and runtime asset paths are updated.
- `npm run gen:types`, `npm run lint`, `npm run check-types`, and `npm run build` pass.
- Manual smoke test confirms comment creation, replies, reactions, task messages, suggestions, task sidebar, gutter icon, and storage watcher still work.

## Dependencies

- Existing `type-crafter` setup in `package.json`.
- Existing `types/index.yaml`, `types/task.yaml`, and `types/storage.yaml` schemas.
- The `~/.fixmycomments/<repo>-<hash>/<branch>/` storage contract shared with the MCP server.
- VS Code native comment APIs and contributed commands in `package.json`.
